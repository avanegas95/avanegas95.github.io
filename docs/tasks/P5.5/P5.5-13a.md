## Goal
The KB becomes the single source the site can render from. Facts that sections need (roles, skills groups, contact links, project card fields) move **verbatim** from KB bodies into typed frontmatter. A single zod schema module serves both the content collections and `kb.ts`. The built prompt stays byte-identical.

## Interfaces
- `kb-schema.ts` exports zod schemas and inferred types:
  - `Role {company; title; employment?; start: "YYYY-MM"; end: "YYYY-MM" | null; showOnSite: boolean; bullets: string[]; note?: string}`
  - `SkillGroup {name; items: string[]}`
  - `ContactLinks {email; linkedin; github}`
  - `location: string`
  - `ProjectCard {status; tech: string[]; links: {repo?; live?}; cover?; featured: boolean}`
  - `bio.headline?`, `bio.lede?` (optional until H4)
  - `VOICE_FIELDS: readonly string[]`: the Anderson-owned field paths, used by 13c
- `site-content.ts` (build-time, `astro:content`): `getBio()`, `getRoles()`, `getSkillGroups()`, `getContact()`, `getPublicProjects()`. Each returns `public: true` entries only, ordered.

## Behaviour / rules
1. Capture the goldens first, from the untouched tree: each KB file's rendered section. After migration, every section (and so the full `buildKb(loadKbSources())`, their sorted concatenation) must be **byte-identical**. `kb.ts` renders the structured fields back to the same markdown (month names, "to present", headings, bullets).
2. If byte identity is impossible for a line, stop and list each differing line in the report. Don't edit a golden to make the test pass.
3. Parse frontmatter with `yaml` in strict mode (unique keys, core schema), then validate with the shared schema. Fail closed with the file path, as today. Keep `kb.ts` runnable under plain `node`. A parity test proves `kb.ts` and the collection loader yield equal data for every KB file.
4. Dates are quoted strings (`"2026-03"`), never YAML dates.
5. Migrate only what sections need. Bodies keep the remaining prose untouched. No KB fact changes: values are moved, not edited.
6. `site-copy.md` template has one heading per slot, each with a one-line instruction and an empty answer area:
   - Hero headline
   - Hero lede ("since 2019", no year count)
   - About
   - per-project description and summary
   The PII guard must stay green on the template, so don't use the words TODO/TBD/placeholder.
7. Token budget ≤ 15k is unchanged, and the system+KB prefix stays deterministic.
